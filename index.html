07Direct physical-disk access

What happens when a user-space executable reaches sector zero?

AnswerA repeated 512-byte zero-write attempt against \\.\PhysicalDrive0.

Five hundred and twelve zero bytes aim at the start of the disk.

Illustrative simulation · no disk access
\\.\PhysicalDrive0 / LBA 0PRESERVED
0–445 bootstrap446–509 partition table510–511 signature
FUN_140011AA0

After a ten-second delay, the worker prepares a zero-filled 512-byte buffer, attempts to open \\.\PhysicalDrive0 with broad access, writes 0x200 bytes, sleeps 200 milliseconds, and repeats.

Legacy MBR: sector zero contains bootstrap code, four partition entries, and the 55 AA signature.

GPT: LBA 0 normally contains a protective MBR. The primary GPT header is typically at LBA 1, so this write alone does not prove full GPT destruction.

Finding 12

0x140011AA0

The clearest code-backed evidence of destructive intent: direct physical-disk access and repeated writes to the beginning of the device.

12What the evidence does not prove

AnswerStatic code establishes capability and intent; it does not prove runtime success or attribution.

Capability is not the same as successful execution.

No dynamic traceThe supplied evidence contains no verified sandbox log, packet capture, or memory-forensics record.

No confirmed disk outcomeThe raw write routine exists; success on a real disk was not independently observed.

No confirmed deletion outcomeWindows protections and locked files may block attempted removals.

Remaining unresolved internalsThe MessageBox swarm helper FUN_14000FBC0, CBT callback FUN_14000E110, and two copy helpers still require separate decompilation.

No attributionPDB names, strings, and mutexes do not identify an author or threat group.

No propagation proofThe static code does not explain how the fictional 340-system incident spread.
